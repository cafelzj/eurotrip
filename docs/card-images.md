旧 27 张候选的审核结论已写入 `research/media/food/candidates.json`；本轮其他已实际看过原图的搜索候选及否决理由见 `food-photo-batch-2026-11-09.json`。通过候选不一定配置，采用情况以 `configuredAssets` 为准。审核记录保存原图 SHA-256、日期和具体结论；搜索结果文字、文件名、许可与测试均不能替代视觉审核。

`data/card-images.js` 的 `assets` 保存尺寸、替代文本、逐图图注、作者、许可链接、来源、原图地址及审核结果；`cards` 指定封面，`galleries` 指定其他合格照片。Wikimedia Commons 与 Open Food Facts 使用各自真实来源。Open Food Facts 照片按其法律说明适用 CC BY-SA 3.0，明确记录产品条码、原上传照片、上传者和所选包装正面，不把数据库许可当图片许可。完整署名见 `assets/photos/LICENSES.md`。

## 中国卡片批量补图的执行方法

当前缺口从[中国卡片补充入口](../research/china/enrichment/README.md)及其最新覆盖清单读取。已保存候选先复核，不重复搜索、下载已有响应；历史批次不重跑。2026-11-17第三批发生过790次Commons搜索尝试中781次429失败，以及1577个猜测文件名仅取得2个候选的低效情况；这些历史记录保留，不能把失败数当作完成量。

1. 每次选取一组具体缺图条目，先看已有候选、否决理由及明确别名，按“已有可核候选／需换来源／缺少具体主体证据”安排后续动作。
2. 新来源先试约12次请求，先检查响应是否真正支持所找对象；持续只有无关结果时换关键词或来源，不扩大低效的全量查询。根据有用候选和实际采用数调整来源顺序，不以搜过、下载过多少张汇报成绩。
3. 元数据先筛具体菜名、品牌、地方变体及使用条件，再下载小组接触表，选出的照片看原图。菜品选清楚、干净的成品近景；标签、包装、工艺与器物按对象选择对应实拍。看不准就留原因，继续处理其他条目。
4. 对确认的图片集中写入正式配置，按实际新增卡片、独立新照片和明确复用分别计数。检查本批列表／详情、手机显示、来源指纹及旧输入，集中更新一次覆盖、索引与归档；没有新变化或失败不反复检查整站。
5. 达到一组可交付增量就发布并核对线上版本，继续处理当前任务的剩余条目。所有缺口继续保留；无法确认不能算补齐，结束回合后不声称仍在后台采集。

共用请求入口仅保存来源响应，不判断照片合格、不自动采用、不直接更新网站：

```sh
python scripts/china-enrichment/fetch_photo_sources.py \
  --plan research/china/enrichment/新批次/source-plan.json \
  --output research/.local/新批次/sources \
  --max-requests 12
```

`source-plan.json` 使用 `{"jobs":[{"url":"https://来源的具体网址","query":"查询词","itemIds":["卡片ID"]}]}`。只接受明确HTTPS来源；源站仍可能返回错误页面，取得响应不表示取得了照片证据。`--cache-log` 可多次提供既有JSONL日志，缓存核对SHA-256后复用原件路径；失败、缓存损坏、限流与未启动的任务分别记录。429响应正文和Retry-After先保存，再暂停该域名；等待时间跨重启生效。连续3次网络失败也暂停该来源，其他来源仍可处理。达到请求预算后剩余任务明确标作未执行，不冒充零结果；不做长时间自动等待或立即反复重试。

通用入口不依赖每批复制脚本。确需来源专用解析时保留一个可参数化适配器；封存批次的脚本仅作历史依据。普通补图轮次约80%的工作应放在检索、人工筛选与采用，约20%用于工具维护、核验和资料整理；这不是降低事实、画面或来源标准的理由。请求机制回归用 `python tests/photo-source-fetch.py` 验证，不为这次工作方式调整重跑网页图片测试。
